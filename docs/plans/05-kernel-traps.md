# Plan 05 — Kernel traps

Depends on [02](02-trips-and-resume.md) for ropcodes and on [03](03-save-unsave.md) if the ROM’s process exit uses `SAVE`. The ROM’s file services call the functions already in `src/trap.lisp`.

Spec: `mmix-doc` §33 and §36–38. MMIX-SIM’s Y-field table stays the user-visible service set.

## Outcome

`TRAP` enters the kernel at `rT` with `rK = 0` and the bootstrap registers set. A dynamic trap enters at `rTT` when `rQ ∧ rK ≠ 0`. `RESUME 1`, executed from a negative address, restores `rK` from `$255` and resumes from `rWW`/`rXX`. A built-in ROM implements Halt and the MMIX-SIM file calls, so user programs keep their current `$255` results.

The default `make-vm` keeps today’s Lisp `exec-trap` until `:kernel t`.

## Current behavior

`exec-trap` (`src/trap.lisp`) handles Y = 0…10 in Lisp. `TRAP 0,0,0` halts. `TRAP 0,0,1` sets `vm-fault` to "TRAP 0,0,1 (no kernel to service the trip)" and halts. Any other Y = 0 halts. Y > 10 sets `vm-fault` and halts. `rK`, `rT`, `rTT`, `rBB`, `rWW`, `rXX`, `rYY`, and `rZZ` are never written by this path. Privileged `PUT` is a silent return (`privileged-special-p`).

## Target behavior

Forced trap, taken by `TRAP` and by any opcode the kernel is emulating:

- `rK ← 0`.
- `rBB ← $255`.
- `rWW ←` the address of the next instruction (`PC+4` for a `TRAP` that has not branched).
- `rXX ←` the instruction, with the high tetra set to `#x80000000` for an ordinary `TRAP`. Software emulation of an opcode uses high tetra `#x02000000`. A translation miss (plan 06) uses `#x03000000`.
- `rYY` and `rZZ` hold the operands the handler needs. For an ordinary `TRAP`, they hold `$Y` and `$Z` when those registers exist; the ROM reads X, Y, and Z from the tetra in `rXX` for the MMIX-SIM dispatch.
- `PC ← rT`.

`RESUME` with `Z = 1`, X = Y = 0, fetched from a negative address:

- Consult `rWW`, `rXX`, `rYY`, `rZZ` in place of `rW`, `rX`, `rY`, `rZ`.
- Ropcodes 0 and 2 work as in plan 02.
- Ropcode 3 installs the page-table entry in `rZZ` for virtual address `rYY` into the data translation cache, or into the instruction cache when the opcode in `rXX` is `SWYM`. Plan 06 owns the cache; this plan stores the pair on the VM so plan 06 can pick it up.
- Then `rK ← $255` and `$255 ← rBB`.
- `Z > 1` sets the `b` bit.

`RESUME 1` fetched from a nonnegative address sets the `k` bit and does not resume.

Dynamic trap, checked at the start of `step-vm` when `:kernel` is set:

- If `rQ ∧ rK ≠ 0`, take the forced-trap sequence with `PC ← rTT` instead of `rT`.
- The instruction that caused a program bit is treated as §37 requires: `x`, `k`, and `b` suppress the instruction; a load with `r` or `n` yields 0; a store with any `rwxnkbsp` bit stores nothing. The trap is precise: later instructions have not retired.
- Security: a nonnegative `PC` with any `rwxnkbsp` bit of `rK` clear sets `s` in both `rQ` and `rK`.

Program bits this plan raises, even before virtual memory:

| Bit | When |
|-----|------|
| `k` | `PUT` of `rC rI rK rQ rT rU rV rTT` while `rK` bit `k` is set; `RESUME 1` from a nonnegative address; `SYNC` with XYZ ≥ 4 (the `SYNC` effect itself is plan 07) |
| `b` | Illegal opcode fields (`GET`/`PUT` with Y ≠ 0, `RESUME` with Z > 1, ropcode > 3), and `PUT` of `rN`, `rO`, or `rS` |
| `n` | A nonnegative instruction uses a negative virtual address |
| `p` | Recorded when the instruction itself came from a negative address. The kernel may run those instructions |

`PUT rQ` keeps any bit that turned on since the last `GET rQ`.

### ROM

Place the ROM at the physical address that a negative `rT` maps to once plan 06 exists. Until then, `:kernel t` sets `rT` and `rTT` to a distinguished negative address and the fetcher, on that address only, runs the Lisp ROM instead of reading `vm-memory`.

The ROM:

- `TRAP` with X = Y = Z = 0: halt, exit code in `$255`, as `halt-vm` does today.
- `TRAP` with X = Y = 0 and Z = 1: stop with the trip reported. This replaces the current fault string.
- X = 0 and Y = 1…10: call `sim-fopen` through `sim-ftell`, then `RESUME 1` so `$255` is the result the Lisp function stored and `rK` returns to the all-ones mask the ROM saved.
- Anything else: halt with `vm-fault` "unsupported TRAP …", the current message.

User-mode `make-vm` does not install the ROM and does not consult `rQ`. `exec-trap` stays the implementation for that path, so the 50 checks keep calling `TRAP` as a Lisp function.

## Design

`src/kernel.lisp`, loaded after `src/trap.lisp`. `make-vm` grows `:kernel`. `step-vm` branches: kernel path calls `deliver-dynamic-trap` then fetch; user path stays as it is.

`vm-rom-base` and a small vector of tetras generated by the s-expression assembler are an alternative to a Lisp ROM. Prefer a real tetra image assembled with `TRAP`’s dispatch written as ordinary MMIX, calling back into Lisp only for the host file operations (a single `SWYM` with an agreed XYZ, documented as the host call, checked so user `SWYM` does not enter it). That keeps the trap entry itself in guest instructions, which is what `RESUME 1` has to return through.

Initial `rK` on a kernel VM is `#xFFFFFFFFFFFFFFFF` after the ROM has started the user, and 0 while the ROM runs. Initial `rT` is the ROM entry.

## Tests

- With `:kernel t`, `TRAP 0,Fputs,StdOut` still appends to `vm-output` and still leaves the character count in `$255`. `rK` is all-ones after the instruction’s trap has returned. `PC` is the instruction after the `TRAP`.
- `TRAP 0,0,0` still halts with `vm-exit-code` equal to `$255`.
- `PUT rK` from a nonnegative `PC` with the `k` bit of `rK` set does not change `rK` and sets the `k` bit of `rQ`.
- `PUT rK` from the ROM’s negative `PC` updates `rK`.
- `rQ` bit set and `rK` masking it on causes the next `step-vm` to enter `rTT` before the user instruction.
- `RESUME 1` from a nonnegative address does not change `PC` to `rWW`.
- Default `make-vm` still passes the existing Fopen, Fgets, Fwrite, and hello tests without entering `rT`.

## Stays unchanged

The Lisp implementations of Fopen through Ftell. Legacy putchar. Trip vectors in nonnegative memory.

## Follow-ons
